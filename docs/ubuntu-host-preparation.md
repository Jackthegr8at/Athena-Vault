# Ubuntu Docker host preparation

Use a supported Ubuntu release and the official Docker Engine/Compose installation instructions for that release. This is a generic preparation checklist, not a firewall policy for any particular network. Decide your own hostname, bind address, client CIDRs, SSH administration account, backup location, and recovery procedure before exposing the service.

1. Apply OS security updates, configure time synchronization, and create a dedicated non-root administration account with only the privileges your deployment needs. Use key-based SSH, verify it in a second session, and keep a console/recovery path available before changing SSH or firewall rules. Keep private keys and credentials off the host checkout and out of Git.
2. Install Docker Engine and the Compose plugin from Docker's official repository. Verify `docker compose version`, daemon health, and access for the intended operator. Docker group membership is effectively root access; grant it deliberately. Do not expose the Docker API/socket to the network or application containers.
3. Prepare an operator-owned application directory (for example `/opt/athena-vault`) and protected backup directory. Keep the environment file mode `0600`; restrict backup and Caddy state directories. Do not copy local `.env*`, workbook files, unencrypted dumps, or workstation SSH keys into a release bundle.
4. Clone or transfer only a reviewed release. Check its checksum/signature through a trusted channel. Copy `.env.docker.example` to a protected ignored file and replace all placeholders with fresh credentials and your own network values. Never reuse example values as production secrets.
5. Keep Caddy bound to loopback during staging. Render `docker compose --env-file .env.docker.prod -f docker-compose.yml -f docker-compose.prod.yml config` and confirm that only Caddy publishes ports. Verify the database volume, service names, image provenance, and internal network before first startup.
6. Before opening the bind address, configure host input and Docker-forwarding firewall rules for your approved client networks. Keep SSH reachable and test from both an allowed and a disallowed client. Use a real HTTPS origin and certificate trust strategy; do not rely on a private hostname alone as authorization.

Continue with [Deployment](deployment.md) for `/setup`, health checks, optional demo, and updates. For a transfer of an existing backup, follow [Ubuntu transfer](ubuntu-transfer.md) and [Backup and restore](backup-and-restore.md); do not restore into the live volume without a separately approved recovery procedure. The application does not configure VPN routing, DNS, router forwarding, host firewall rules, or external reverse-proxy state for you.
